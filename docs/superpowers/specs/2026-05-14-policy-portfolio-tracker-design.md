# Policy Portfolio Tracker

**Status:** Design — not yet implemented
**Date:** 2026-05-14
**Builds on:** `2026-05-14-chart-axes-p-percentiles-warranty-tiers-design.md`

## Goal

Add a portfolio-level view that captures warranty quotes generated by `/run`, tracks their lifecycle (`pending_quote` → `approved` / `rejected`), and computes program-wide actuarial roll-up math (premium collected, expected claims, program loss ratio, modeled profit) across the *active approved* policies.

Storage piggy-backs on the Google Sheet already wired up for submission logging (`GSHEETS_SHEET_ID` / `GSHEETS_SERVICE_ACCOUNT_JSON`), in a new worksheet called `Policies`.

## What changes

| Column | Type | Source / notes |
|---|---|---|
| `policy_id` | string | auto: `pol-YYYYMMDD-NNN`, sequential per day |
| `created_at` | ISO timestamp | server time at save |
| `status` | enum | `pending_quote` (default) · `approved` · `rejected` |
| `funding_model` | enum | `base` · `full` — picked at save time |
| `property_name` | string | from /run form |
| `contact_name` | string | from /run form |
| `contact_email` | string | from /run form |
| `property_type` | string | from /run form |
| `num_units` | int | from /run form |
| `standard_price` | number | from pricing lookup |
| `coverage_per_unit` | number | from warranty.target_terms |
| `coverage_total` | number | from warranty.target_terms |
| `claim_probability` | float | `summary[funding_model].prob_assessment.yr_1_5` — the 1–5yr P(SA) for the chosen funding model |
| `warranty_premium_default` | number | from warranty.target_terms |

The Sheet header row is auto-created on first write, matching the existing pattern in `_log_submission_to_sheets`.

### Save flow on the results page

A new card at the bottom of `templates/results.html` titled "Save This Quote", rendered only when the warranty analysis succeeded AND the Sheet is configured (`GSHEETS_*` env vars set).

The card contains:
- A radio group `funding_model` with `base` and `full` — required, no default
- A `<select>` `status` with options `pending_quote` (default), `approved`, `rejected`
- A `Save policy` submit button
- Hidden inputs carrying the data needed to materialize a Policies row: `property_name`, `contact_name`, `contact_email`, `property_type`, `num_units`, `standard_price`, `coverage_per_unit`, `coverage_total`, `claim_probability_base`, `claim_probability_full`, `warranty_premium_default`, `warranty_premium_charged_base`, `warranty_premium_charged_full`, `verdict_base`, `verdict_full`

The route handler picks the per-model values based on the chosen `funding_model`.

### `POST /save-policy`

Reads the form, builds the row payload, calls `policies.save_policy()`, redirects to `/portfolio?just_saved=<policy_id>` on success or back to a small error page on failure. Password gate applies (same `ACCESS_PASSWORD` as everywhere else).

### `GET /portfolio`

Reads query params for `status_filter` (multi-select; default `["approved"]`) and `search` (free-text matched against `property_name` and `contact_email`, case-insensitive).

Renders `templates/portfolio.html`:

1. **Program Summary card** — fixed to approved policies regardless of the filter:
   - Active policies count
   - Total premium collected (`total_premium`)
   - Total coverage exposure (`total_coverage`)
   - Sum of expected claims (`expected_claims`) — "Σ coverage × P(claim)" subtitle
   - Program loss ratio (`program_loss_ratio`) as a percent
   - Modeled program profit (`modeled_profit`)
   - Footer note: "Modeled — based on claim probabilities at quote time, not realized claims."

2. **Filter bar** — status checkboxes (Pending / Approved / Rejected, with current selection pre-checked) + a text input for search. Submits a GET with updated query params.

3. **Policies table** — one row per filtered policy with columns:
   - Policy ID
   - Created (date only, e.g. `2026-05-14`)
   - Property name
   - Funding model (base/full as a badge)
   - Status (as a colored badge)
   - Premium charged
   - Coverage total
   - Claim probability (%)
   - Verdict (badge)
   - Actions: buttons appropriate to current status. The button set per status:
     - `pending_quote` → `Approve`, `Reject`, `Delete`
     - `approved` → `Reject`, `Delete`
     - `rejected` → `Approve`, `Delete`

If `?just_saved=<id>` is present, show a flash banner "Policy `pol-…` saved" above the table.

### Action endpoints

- `POST /portfolio/<policy_id>/approve` → `policies.update_policy_status(id, "approved")`, redirect to `/portfolio`
- `POST /portfolio/<policy_id>/reject` → `policies.update_policy_status(id, "rejected")`, redirect to `/portfolio`
- `POST /portfolio/<policy_id>/delete` → `policies.delete_policy(id)`, redirect to `/portfolio`

All three preserve the current filter/search params via the `Referer` header or a hidden form input (whichever ships cleaner — the implementation plan decides).

### Header navigation

Add a single button to the existing header on the landing page and the pricing page:

```
[← New Test]  [📊 Portfolio]  [⬇ Download CSV]
```

The Portfolio button on the results page links to `/portfolio` directly.

## Concurrency + edge cases

- **Concurrent status changes:** `update_policy_status` re-fetches the row by `policy_id` immediately before writing, so two near-simultaneous status changes don't silently clobber each other. Not transactional. At single-operator scale this is sufficient; flagged for revisit if multiple admins start using it.
- **Deleted while viewing:** if a user clicks Approve on a row that's been deleted, the action endpoint returns `False` from `update_policy_status` and flashes "Policy `pol-…` not found — refresh and try again."
- **`policy_id` collision:** at save time, read the Policies sheet, count rows whose `policy_id` starts with `pol-<today>-`, and use that count + 1 as the next sequence number. At single-writer scale this is safe; flagged for revisit if writes become concurrent.
- **Sheet quota:** Google Sheets API has a 60 reads/min and 60 writes/min per service account quota. Well above this app's load (single-operator). No special handling.

## Out of scope

- Actual realized claims tracking (only modeled / expected claims here; "did this policy actually claim?" is a future iteration)
- Multi-user auth or audit log
- Bulk operations (approve all, export filtered subset)
- Edit existing policy details (only status changes via the lifecycle endpoints; delete + re-save for full edits)
- Sheet write throttling — relying on Google's 60/min default quota
